---START---

Applying the **Risk-Based Testing (RBT)** strategy, please generate a detailed list of Test Cases from the High-Level Scenarios reviewed in Step 4.

## Requirements for each Test Case:

### 1. Risk Assessment

Assess the **Risk Level** for each Module/Feature:
- **High Risk:** Core business logic, involving money/security, many dependent users → Generate many test cases, test thoroughly
- **Medium Risk:** Important feature but not critical → Moderate testing
- **Low Risk:** Secondary feature, low impact → Basic testing, happy path only

### 2. Test Case Structure

Each Test Case must include all fields:

| Field | Requirement |
|-------|------------|
| **Module / Sub-module** | Module name as decomposed in Step 3 |
| **Test Case Title** | Concise title, clearly stating the purpose |
| **Pre-conditions** | Prerequisites before executing the test |
| **Test Steps** | Execution steps, **numbered sequentially** |
| **Expected Results** | Expected outcomes corresponding to each step, **numbered** |
| **Test Data** | Concrete data (see rules below) |
| **Priority** | High / Medium / Low |
| **Risk Level** | High / Medium / Low |

### 3. Test Data Rules

Test Data **MUST BE CONCRETE**, do not use generic descriptions:

```
❌ WRONG: "Enter a valid email"
✅ CORRECT: "Enter email: test_customer_01@domain.com"

❌ WRONG: "Enter a valid code"
✅ CORRECT: "Enter code: CUST-2026-0012"

❌ WRONG: "Enter an invalid phone number"
✅ CORRECT: "Enter phone: abc123xyz (letters instead of digits)"

❌ WRONG: "Enter a name that is too long"
✅ CORRECT: "Enter name: [string of 256 consecutive 'A' characters] (exceeds 255 limit)"
```

### 4. Coverage Scope

Ensure Test Cases cover a diverse range:
- **Happy Path:** Main flow runs smoothly
- **Negative Path:** Invalid input, missing data, wrong format
- **Boundary Values:** Boundary values (min, max, min-1, max+1)
- **Edge Cases:** Timeout, connection loss, concurrent access

[Additional hints (customize per project):
- Authorization: What User role A can/cannot do
- Compatibility: Responsive design, multi-browser
- Performance: Handling large datasets (1000+ records)
- ...]

### 5. Test Design Techniques

Apply the following classic techniques to generate systematic test cases:

**a) Equivalence Partitioning**
Divide input data into equivalent classes; only one representative value per class needs testing.
```
Example for the "Age" field (valid: 18-60):
- Valid class: 25 (representative of 18-60)
- Invalid lower class: 10 (representative of <18)
- Invalid upper class: 70 (representative of >60)
```

**b) Boundary Value Analysis (BVA)**
Test values at the boundaries: min, min+1, max-1, max, min-1, max+1.
```
Example for the "Password" field (6-20 characters):
- 5 characters (lower boundary -1) → Error expected
- 6 characters (lower boundary)    → Valid
- 7 characters (lower boundary +1) → Valid
- 19 characters (upper boundary -1) → Valid
- 20 characters (upper boundary)    → Valid
- 21 characters (upper boundary +1) → Error expected
```

**c) Decision Table**
Use when logic involves multiple combined conditions (AND/OR). List condition combinations → outcomes.
```
Example for the "Login" function:
| Valid Email | Correct Password | Active Account | Result            |
|:---:|:---:|:---:|---|
| ✅ | ✅ | ✅ | Login successful     |
| ✅ | ❌ | ✅ | Wrong password error |
| ❌ | ✅ | ✅ | Email not found error |
| ✅ | ✅ | ❌ | Account locked error |
```

**d) State Transition**
Use for objects with multiple state changes (workflow, order status...).
```
Example for Order status:
New → Processing → Shipping → Completed
                  → Cancelled
Test: Every valid transition + INVALID transitions (e.g., Completed → New)
```

> Choose the appropriate technique for each Module/Field based on data characteristics and business logic.
